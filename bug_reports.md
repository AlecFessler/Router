### SEC-STATE-01: DHCPDECLINE/DHCPRELEASE are not bound to the client MAC, so a spoofed client-id deletes another client's lease and permanently excludes the address
- **Branch:** `bug/state-dhcp-decline-spoof`
- **Severity:** high
- **Component:** `src/protocols/dhcpv4.zig:377` (DECLINE) and `:391` (RELEASE); `src/tables/dhcp_table.zig:245-266` (`release`/`decline` take no MAC)
- **Bug:** A DHCPv4 lease is bound to both the client identifier (option 61) and the chaddr MAC: `DhcpTable.bindOrRenew` rejects a renew with `error.InvalidMac` when the MAC does not match the existing entry. `release()` and `decline()` never receive or check the MAC; they only look the lease up by client identity. The LAN handler also echoes the attacker's client-id back and acts on it. Consequently any LAN host can spoof another client's client-id (option 61) and: (a) DHCPDECLINE the victim's *bound* address, which deletes the victim's live lease and appends the address to `excluded_ips` **permanently** (the table has no expiry for excluded addresses; see the TODO at `dhcp_table.zig:262`); or (b) DHCPRELEASE the victim's lease, returning the address to the free pool so the attacker can immediately re-bind it (double allocation / IP theft). Repeating (a) 253 times permanently exhausts the whole `/24` pool and no client can ever obtain an address again until reboot.
- **Trigger:** victim sends DISCOVER/REQUEST with client-id `victim-client` from MAC V and is ACKed 192.168.86.10; attacker sends a DHCPDECLINE (op BOOTREQUEST, server-id 192.168.86.1, requested-IP 192.168.86.10, client-id `victim-client`) from a *different* MAC A.
- **Expected (safe):** a DECLINE/RELEASE must only affect a lease owned by the sending client, i.e. the client-id **and** the chaddr MAC must match the stored entry (as `bindOrRenew` already enforces); otherwise drop the message and leave the victim's lease and the free pool untouched.
- **Actual:** the victim's entry is removed (`lookupByClient` returns null) and 192.168.86.10 is moved to `excluded_ips`, so the victim loses its address and the address is never handed out again.
- **Repro test:** `test_fixtures/regression_tests.zig` test `"SEC-STATE-01: DHCPDECLINE from a different MAC must not delete another client's lease"` (fails on branch at `lookupByClient` after the spoofed DECLINE).
- **Suggested fix (not applied):** pass a MAC into `DhcpTable.decline`/`release` and require it to match the stored lease MAC before removing anything (only allow DECLINE for `offered` leases), and give `excluded_ips` a quarantine deadline so spoofed DECLINEs cannot permanently exhaust the pool. Note the MAC used must be the **Ethernet source MAC**: the DHCP handler currently takes `mac` from the payload `chaddr` (`dhcpv4.zig:361`), which is attacker-controlled, so a table-level MAC check alone is only as strong as the caller's MAC source. This raises the bar (an attacker must also spoof the victim's MAC) but does not authenticate DHCP; the report is about the missing consistency check `bindOrRenew` already enforces.
- **Notes:** the same missing check exists for DHCPRELEASE; a handler-level test would also fail. Client ids are attacker-chosen on a LAN, so this is reachable by any unauthenticated host on the segment.

### SEC-FWD-01: LAN datagrams to loopback/"this network"/link-local/reserved destinations are NATed and forwarded to the WAN
- **Branch:** `bug/forwarding-bogon-dst`
- **Severity:** medium
- **Component:** `src/protocols/ipv4.zig:431` (`classifyDestination`) and `src/protocols/ipv4.zig:203` (`forwardNat` LAN branch)
- **Bug:** `classifyDestination` only recognizes the limited broadcast, the LAN directed broadcast, 224.0.0.0/4 multicast, the router's own LAN/WAN addresses and the LAN subnet; everything else is classified `.wan`. `forwardNat`'s LAN branch forwards every destination classified `.wan`, inserts a NAT mapping, and transmits the datagram on the WAN. As a result the router will NAT and send datagrams addressed to 0.0.0.0/8 ("this network"), 127.0.0.0/8 (loopback), 169.254.0.0/16 (link-local) and 240.0.0.0/4 (reserved/class E) out the ISP uplink. None of these destinations can be valid on the WAN link, so the traffic is both leaked to the ISP and (for loopback, if the next hop routes 127/8, which is uncommon) could reach loopback-bound services on that next hop. The same classification also lets non-LAN RFC 1918 destinations (10/8, 172.16/12, 192.168/16 other than the LAN) and the WAN subnet's own directed broadcast be forwarded onto the WAN.
- **Trigger:** LAN host 192.168.86.42 sends a UDP datagram (source port 40000, valid IPv4 checksum) to 127.0.0.1:53. `Ethernet.handle` -> `IPv4.handle` -> `Udp.handle` -> `forwardNat(.lan)`: `classifyDestination(127.0.0.1)` returns `.wan`, a NAT mapping is inserted, and the frame is rewritten (src 203.0.113.50:40000) and transmitted on the WAN interface.
- **Expected (safe):** drop the datagram on ingress (no NAT mapping, no transmission), because 0/8, 127/8, 169.254/16 and 240/4 are non-routable destinations. RFC 1122 §3.2.1.3, RFC 1812 §3.3.6 and RFC 3927 §7 require the router to discard them.
- **Actual:** `h.txCount()` is 1 and `h.dropCount()` is 0 for every forbidden destination; the test fails at `expectEqual(0, h.txCount())`. The observed transmission was `egress=wan 203.0.113.50 -> 127.0.0.1`.
- **Repro test:** `test_fixtures/regression_tests.zig` test `"SEC-FWD-01: datagrams to loopback/this-network/link-local/reserved destinations must not be forwarded to the WAN"` (fails on branch).
- **Suggested fix (not applied):** classify these ranges as droppable (e.g. an `.invalid`/`.drop` class) and reject them in `forwardNat` before the NAT insert; also consider the WAN subnet broadcast and RFC 1918 destinations not routed through the LAN.
- **Notes:** non-first fragments take the same decision through `classifyDestination(...) == .wan` in `IPv4.handle`; `sendTtlExceeded` also emits an ICMP error for these destinations instead of dropping. Private-network destinations were left out of the test so the asserted expectation stays uncontroversial; they are noted here for completeness.

### SEC-FWD-02: WAN ingress accepts LAN-side/martian source addresses and delivers them to LAN clients (gateway impersonation)
- **Branch:** `bug/forwarding-wan-spoofed-src`
- **Severity:** medium
- **Component:** `src/protocols/ipv4.zig:244` (`forwardNat` WAN branch; only `dst == lease.ip` and the NAT port are checked, never `src`)
- **Bug:** The WAN-to-LAN path validates only the destination address (`dst == wan_lease.ip`) and that the transport port has an inbound NAT mapping. The packet's source address is never sanity-checked, so a datagram arriving from the WAN can claim any source, including the LAN subnet (192.168.86.0/24), the router's own LAN address, 127/8, 0/8, 169.254/16, multicast and broadcast. Such a packet is translated (`dst` -> inside client) and delivered to the LAN client unchanged, so the client sees a datagram that claims to come from its default gateway or from a LAN peer. A WAN-side attacker only has to know (or guess/scan) the public port of any open mapping - which is often preserved from the client's own source port - to inject spoofed replies (e.g. spoofed DNS answers "from the gateway" to port 53, or forged traffic to any service that trusts the LAN gateway address).
- **Trigger:** LAN client 192.168.86.42 sends one UDP datagram from port 40000 to 8.8.8.8:53 (this creates the mapping 203.0.113.50:40000 -> 192.168.86.42:40000). A WAN sender then transmits a UDP datagram with source 192.168.86.1:53 and destination 203.0.113.50:40000. `forwardNat(.wan)` finds the inbound mapping and forwards the datagram to 192.168.86.42 with source 192.168.86.1:53.
- **Expected (safe):** drop any WAN-ingress datagram whose source address is on the LAN subnet, is one of the router's own addresses, or is otherwise non-routable (0/8, 127/8, 169.254/16, 224/4, 255.255.255.255); a source on the LAN cannot legitimately arrive from the WAN, and accepting it is an anti-spoofing (BCP 38 / RFC 2827) violation. No NAT state should be touched.
- **Actual:** `h.txCount()` is 1 and `h.dropCount()` is 0 for every spoofed source; the observed transmission was `egress=lan 192.168.86.1 -> 192.168.86.42`. The test fails at `expectEqual(0, h.txCount())` on the first source (192.168.86.1).
- **Repro test:** `test_fixtures/regression_tests.zig` test `"SEC-FWD-02: WAN ingress datagrams with LAN-side or martian sources must be dropped"` (fails on branch).
- **Suggested fix (not applied):** validate `ip_view.get(.src)` in the `forwardNat` `.wan` branch (and in `IPv4.handle` for fragments): drop if `classifyDestination(src)` is `.local`, `.lan`, `.broadcast` or `.multicast`, or if the source is in 0.0.0.0/8, 127.0.0.0/8, 169.254.0.0/16 or 240.0.0.0/4.
- **Notes:** related to SEC-FWD-01 (same missing bogon policy on the destination side of the LAN->WAN path). Deliberately does not report endpoint-independent NAT acceptance of arbitrary off-link sources (RFC 4787 behaviour) - only sources that are impossible on the WAN link. Requires an existing mapping, so this is source spoofing rather than a mapping bypass.
### SEC-STATE-02: NAT mappings are endpoint-independent and inbound lookups never validate the remote peer, so any Internet host can inject packets into an inside host's mapping
- **Branch:** `bug/state-nat-inbound-any-peer`
- **Severity:** medium
- **Component:** `src/tables/nat_table.zig:51-57` (`Key` has no peer), `:95-112` (`inboundLookup`/`inboundEntry`); used by `src/protocols/ipv4.zig:248-255`
- **Bug:** A NAT mapping is keyed only by `(protocol, router WAN ip, external port)`; the destination the inside host originally sent to (remote address + port) is not part of the mapping, and `inboundEntry` accepts a packet from *any* source. The router therefore performs endpoint-independent ("full cone") filtering: after an inside host sends one datagram to 8.8.8.8:53, any host on the Internet can send a datagram to `wan_ip:<external port>` and it is delivered to that inside host with the attacker's (arbitrary, spoofable) source address intact. Since the external port is chosen as the inside source port whenever it is free (`PortAllocator.allocate` prefers `key.port`), the mapping is also predictable. An off-path attacker can use this to inject spoofed UDP/TCP packets (e.g. forged DNS responses, TCP RSTs) into connections the inside host believes are peer-restricted, and can reach inside hosts that never spoke to the attacker.
- **Trigger:** inside host 192.168.86.42:40000 sends one UDP datagram to 8.8.8.8:53 (creates a mapping with external port 40000); WAN peer 6.6.6.6:1234 then sends a UDP datagram to the WAN lease IP:40000.
- **Policy assumption:** the project documents no intended NAT filtering mode, so this is a hardening finding, not an unambiguous memory-safety bug. The test encodes the behaviour expected of a residential router: address/port-restricted cone (RFC 4787 REQ-7/REQ-8 style) rather than endpoint-independent filtering. It is reported because the router's NAT is its only inbound filter and the repo treats untrusted peers as in scope.
- **Expected (safe):** an inbound packet must only be delivered if its source endpoint matches an endpoint the inside host actually sent to through that mapping (address- or endpoint-dependent filtering); a datagram from an unrelated peer must be dropped.
- **Actual:** the datagram from 6.6.6.6:1234 is forwarded to 192.168.86.42:40000 (TX count goes from 1 to 2, nothing dropped).
- **Repro test:** `test_fixtures/regression_tests.zig` test `"SEC-STATE-02: a NAT mapping only accepts inbound packets from the peer the inside host sent to"` (fails on branch at the post-injection `txCount` assertion).
- **Suggested fix (not applied):** store the originally contacted remote endpoint(s) with the mapping and require `src == peer` on inbound lookups (address-restricted cone), or at minimum require the inbound source port to match the destination port the inside host used.
- **Notes:** independent of SEC-STATE-01. Distinct from SEC-FWD-02 (WAN-ingress source-prefix/martian filtering): that bug is about accepting LAN/martian *source addresses* on ingress and is fixed by source-prefix validation; this one is about not binding a mapping to the peer the inside host contacted and is fixed by peer binding in the NAT table. The same peer-unaware lookup also feeds ICMP error translation (`forwardQuotedError`), so fixing the mapping key would also harden SEC-FWD-03's match.

### SEC-FWD-03: ICMP quoted errors are matched against NAT flows by the quoted source port only, so off-path errors can be injected into any mapped connection
- **Branch:** `bug/forwarding-icmp-error-quote`
- **Severity:** medium
- **Component:** `src/protocols/icmpv4.zig:99` (`forwardQuotedError`, WAN branch at `:135-150`); `src/tables/nat_table.zig:51` (a NAT mapping records no remote endpoint)
- **Bug:** For an ICMP error arriving on the WAN (`destination_unreachable` codes 1/3/4 or `time_exceeded`), `forwardQuotedError` validates only that the outer destination is the public IP, that the quoted packet's source is the public IP, and that `(protocol, quoted-src-ip, quoted-src-port)` exists in the NAT table. The quoted packet's **destination** address/port - i.e. which peer the client was actually talking to - is never compared with the flow, because the NAT mapping stores no remote endpoint. The error is then rewritten (quoted source -> client address/port, outer destination -> client) and delivered to the LAN client. A WAN sender that knows or guesses the public port of any mapping can therefore forge an ICMP error quoting a datagram to an arbitrary destination; because the router launders the quote into the client's own address/port, the client's stack accepts it as an error about its real connection and can abort, reset or shrink (PMTU) that connection. The client is not required to have ever sent anything to the quoted destination.
- **Trigger:** LAN client 192.168.86.42 opens UDP 40000 -> 8.8.8.8:53, creating the public mapping 203.0.113.50:40000 -> 192.168.86.42:40000. A WAN sender then sends an ICMP destination-unreachable/port-unreachable (type 3 code 3) to 203.0.113.50 whose quoted datagram is `203.0.113.50:40000 -> 198.51.100.99:53` (a destination that has never been contacted). The router finds the mapping from the quoted source port, rewrites the quote's source to 192.168.86.42:40000, sets the outer destination to 192.168.86.42, and transmits it on the LAN.
- **Expected (safe):** drop the ICMP error, because the quoted datagram does not correspond to any existing mapping (the only mapping peers with 8.8.8.8:53). RFC 4787 REQ-10 requires a NAT to silently discard ICMP errors that do not match an existing mapping. A legitimate error quoting `203.0.113.50:40000 -> 8.8.8.8:53` must still be translated and delivered (positive control included in the test).
- **Actual:** the forged error is forwarded to the client (`txCount()` is 1 instead of 0); the test fails at `expectEqual(0, h.txCount())`. The observed transmission is `egress=lan 8.8.8.8 -> 192.168.86.42` with the quoted source rewritten to `192.168.86.42:40000` and the quoted destination left as `198.51.100.99:53`.
- **Repro test:** `test_fixtures/regression_tests.zig` test `"SEC-FWD-03: ICMP errors quoting a packet outside the sender's flow must not be forwarded"` (fails on branch).
- **Suggested fix (not applied):** record the remote endpoint (outbound destination IP and port) in each NAT mapping and, in `forwardQuotedError`, require the quoted packet's destination address/port to equal the mapping's remote endpoint before rewriting and forwarding. Do **not** substitute a check that the ICMP error's own source equals the quoted destination: legitimate errors from mid-path routers (e.g. fragmentation-needed) quote the original datagram but are sourced by an intermediate router, so that check would drop valid PMTU errors - which is why the test asserts on the quoted flow instead.
- **Notes:** the mirror (LAN-originated) branch at `src/protocols/icmpv4.zig:151` has the same missing ownership check: a LAN host can forge an ICMP error that quotes another LAN host's flow (`outboundLookup` is keyed by the quoted destination only) and the router will forward it to the WAN peer with the public source address rewritten, letting one LAN client abort another's connections. Fragments (quoted `fragment_offset != 0`) are already rejected. Same root cause could be filed once with the NAT-table peer-tracking fix.
- **Extended repro (LAN-origin mirror, same branch/test):** `bug/forwarding-icmp-error-quote` now also covers the mirror direction in the same test. Two LAN clients each hold a live mapping (.42:40000 -> 8.8.8.8:53 and .43:40001 -> 8.8.8.8:53); client .42 then sends an ICMP fragmentation-needed whose outer destination is 8.8.8.8 and whose quoted packet is `8.8.8.8:53 -> 192.168.86.43:40001`. Expected: drop, because the error's sender (.42) is not the host the quoted packet was addressed to, so it is not .42's error to report. Actual: `outboundLookup` is keyed by the quoted destination only, so the router rewrites the quote to the public identity (quoted dst -> 203.0.113.50:40001), sets the outer source to the public address, and transmits it to 8.8.8.8 - i.e. any LAN host can make the router deliver an ICMP error about another LAN host's connection to the WAN peer (connection reset / PMTU poisoning between LAN clients, with the forgery laundered through the router's public address). Positive control: .43's own error about the same flow is still relayed (outer src 203.0.113.50, quote dst rewritten to 203.0.113.50:40001). Test fails first at the LAN phase (`expected 0, found 1`); the WAN phase and both positive controls pass after the fix. Fix for this direction: additionally require the quoted packet's destination to equal the ICMP error's outer source (`quote.dst == outer.src`) in the `.lan` branch - valid for endpoint-originated LAN errors (no mid-path-router caveat) - on top of the peer/ownership tracking needed for the WAN branch.

### SEC-STATE-03: NAT table capacity is shared with no per-source accounting or eviction, so one LAN host can deny NAT service to every other host
- **Branch:** `bug/state-nat-capacity-dos`
- **Severity:** medium
- **Component:** `src/tables/nat_table.zig:146-152` (`insert` returns `error.NoCapacity` once `inside.count() == capacity`; only already-expired entries are ever removed), `src/protocols/ipv4.zig:219-224`
- **Bug:** The NAT table is a single global array with a fixed capacity (16384 in `src/main.zig`, shared by TCP/UDP mappings) and no per-source quota. Once it is full, `NatTable.insert` returns `error.NoCapacity`; `forwardNat` propagates the error, so the packet is dropped and an error is logged. There is no eviction of live mappings and no reservation for other hosts, so a single unauthenticated LAN host can create 16384 mappings (64K source ports available; one UDP datagram per port) and then keep them alive by refreshing every UDP_NAT_TIMEOUT (300 s) or TCP_NAT_TIMEOUT (7440 s). Every other host's *new* outbound connections are then dropped for as long as the attacker keeps the table full; only pre-existing mappings continue to work. The same capacity is also the only limit on per-host state, so the exhaustion is cheap (~16k small packets).
- **Policy assumption:** a bounded NAT table is by design; the bug is the absence of any fairness/reclamation when one source exhausts it, not the bound itself. The test requires only that a different host's new flow is not denied (quota or LRU both pass).
- **Trigger:** with `nat_capacity = 2`, host 192.168.86.42 sends UDP datagrams from source ports 40000 and 40001 to 8.8.8.8:53 (2 mappings, table full); host 192.168.86.43 then sends its first datagram to 8.8.8.8:53.
- **Expected (safe):** exhausting the table from one source must not deny NAT service to a different source: the router must reclaim capacity (e.g. evict the oldest/least-recently-used mapping, or enforce a per-source quota) and forward the new flow.
- **Actual:** the third datagram is dropped with `error.NoCapacity`; only 2 packets are transmitted instead of 3 (and one handler error is recorded).
- **Repro test:** `test_fixtures/regression_tests.zig` test `"SEC-STATE-03: one LAN host exhausting the NAT table must not deny NAT service to other hosts"` (fails on branch at the `txCount() == 3` assertion).
- **Suggested fix (not applied):** add per-source mapping quotas and/or LRU eviction of live mappings at capacity; return an ICMP error to the offending flow instead of silently dropping unrelated flows. This test accepts either fix (quota or eviction) because it only requires that host B is not denied.
- **Notes:** with the production capacity this needs ~16k packets from one LAN host. Independent of SEC-STATE-01/02; no duplicate root cause. Similar in shape to DHCP pool exhaustion (SEC-STATE-01 notes) but a different table and fix.

### SEC-FWD-04: The ICMP echo responder answers requests whose source IP or Ethernet source is a group/martian address, turning the router into a broadcast/multicast reflector
- **Branch:** `bug/forwarding-echo-source-reflection`
- **Severity:** medium
- **Component:** `src/protocols/icmpv4/echo.zig:87-106` (the reply path; in contrast `src/protocols/icmpv4/time_exceeded.zig:84-87` performs exactly this source validation before emitting a time-exceeded error)
- **Bug:** Before answering an echo request the responder only checks that the destination is one of the router's own addresses. It never validates the request's source: `sender_ip = ip_view.get(.src)` is copied into the reply's destination and `ethernet_view.get(.src_mac)` is copied into the reply's destination MAC. So an echo request whose L3 source is 255.255.255.255, a multicast address, 0.0.0.0 or 127.0.0.1 produces a reply transmitted to that same address, and an Ethernet source with the I/G (group) bit set produces a reply addressed to that group MAC. `sendTtlExceeded` already rejects both (`sender_ip[0] == 0 || 127 || >= 224`, broadcast class, and `sender_mac[0] & 1 != 0`), so the omission is inconsistent with the router's own policy. Impact: an attacker who can send to the WAN interface can spoof a ping's source as the limited broadcast or a multicast address (and/or a broadcast MAC) and make the router emit a full-size ICMP echo reply to that group address on the ISP link - a reflected broadcast/multicast reflector (one spoofed datagram becomes one reply delivered to every host on the segment; 1:1 fan-out, not byte amplification). It is also an IEEE 802.3 violation to treat a group MAC as a sender address.

- **Expected (safe):** drop the request without emitting anything when the source IP is 0.0.0.0/8, 127.0.0.0/8, 224.0.0.0/4, the limited broadcast, or a broadcast-class destination, or when the Ethernet source MAC has the group bit set (IEEE 802.3 unicast source requirement; same check `sendTtlExceeded` uses). A normal unicast request to the router's WAN address must still be answered.
- **Actual:** `h.txCount()` is 1 for every forbidden source and the emitted frame is `egress=wan dst_ip=255.255.255.255` (and `dst_mac=ff:ff:ff:ff:ff:ff` for the broadcast-MAC case); the test fails at `expectEqual(0, h.txCount())` on the first case.
- **Repro test:** `test_fixtures/regression_tests.zig` test `"SEC-FWD-04: ICMP echo requests from broadcast/multicast/martian sources must not be answered"` (fails on branch; includes a passing positive control for an ordinary WAN ping).
- **Suggested fix (not applied):** before building the reply in `Echo.handle`, apply the same source sanity checks as `sendTtlExceeded` (reject `sender_mac[0] & 1 != 0`, `sender_ip[0] == 0`, `== 127`, `>= 224`, and `classifyDestination(sender_ip) == .broadcast`) and release the buffer.
- **Notes:** the identical group-MAC/source-address problem exists on the ARP responder/learning path (`src/protocols/arp.zig:109-141`) and is reported separately as it corrupts neighbour state rather than emitting a reflected reply.
### SEC-PARSE-02: ICMPv4 zero checksum is treated as "validation disabled", so corrupt messages are acted on
- **Branch:** `bug/parsing-icmp-zero-checksum`
- **Severity:** medium
- **Component:** `src/protocols/icmpv4.zig:53-58` (`ICMPv4.validate`)
- **Bug:** `validate()` short-circuits with `if (view.get(.checksum) == 0) return;`, copying the UDP rule (RFC 768 allows a zero UDP checksum to mean "not computed" for IPv4). ICMPv4 has no such convention (RFC 792): the checksum field always carries the one's-complement checksum of the message, and zero is just one possible valid value. A message whose checksum field is 0 while its computed checksum is non-zero is therefore corrupt, but it skips validation entirely and is parsed, dispatched and acted upon. For echo requests addressed to the router, `Echo.handle` answers it; the incremental reply-checksum update starts from the bogus 0 field, so the router emits an echo reply whose ICMP checksum is itself invalid. For ICMP error messages the router recomputes the checksum after rewriting the quoted packet, effectively laundering an unauthenticated message into a checksum-valid one for the LAN client.
- **Trigger:** LAN Ethernet frame -> IPv4 (protocol 1) -> ICMPv4 echo request (`type=8`, `code=0`, valid id/seq/data) with the checksum field forced to `0x0000` while the true checksum of the body is non-zero. Framed/sent with an otherwise valid IPv4 header.
- **Expected (safe):** perform the RFC 792 checksum verification unconditionally; a zero/incorrect checksum is an invalid message and must be dropped (no echo reply, no error forwarding).
- **Actual:** `validate()` returns success without computing the checksum; the echo request is answered. The test's positive control (same bytes with a computed checksum) sends one reply; the zero-checksum variant also sends one reply, so `txCount` is 1 where 0 is required.
- **Repro test:** `test_fixtures/regression_tests.zig` test `"SEC-PARSE-02: an ICMPv4 message with an invalid zero checksum must not be acted on"` (fails on branch: expected 0 TX, found 1; full suite otherwise green).
- **Suggested fix (not applied):** remove the `checksum == 0` early return in `ICMPv4.validate` and always run `checksum.addFields(.message_type, .payload)` + `checksum.validate()`.
- **Notes:** same short-circuit pattern is legitimate for UDP (`udp.zig:35`) but not ICMPv4. A zero checksum that is *mathematically valid* for the message still passes the unconditional check, so removing the short-circuit does not reject legal traffic.

- **Branch:** `bug/forwarding-arp-group-mac`
- **Severity:** medium

- **Bug:** `Arp.handle` validates the ARP field/opcode metadata but never validates the sender hardware address. - **Actual:** the forged reply is cached (`State.wan_arp_table.lookup(203.0.113.1)` becomes ff:ff:ff:ff:ff:ff) and the next forwarded datagram goes out with `dst_mac=ff:ff:ff:ff:ff:ff`; the test fails at the first assertion with `expected 02:99:88:77:66:55, found ff:ff:ff:ff:ff:ff`.
- **Repro test:** `test_fixtures/regression_tests.zig` test `"SEC-FWD-05: ARP must not learn a group sender MAC as a neighbour"` (fails on branch).
- **Suggested fix (not applied):** in `Arp.handle`, reject `sender_mac[0] & 1 != 0` before replying or caching (both request and reply branches); additionally make `ArpTable.cache` refuse group MACs as defence in depth.
- **Notes:** same class as SEC-FWD-04 (echo responder) but the consequence is persistent neighbour corruption rather than a reflected reply, so it is filed separately. Requires only on-link access to the WAN L2 segment; no NAT mapping is needed.
- **Corroborating repro (LAN request variant):** `bug/parsing-arp-group-mac` @ 3e191fc — test `"SEC-PARSE-01: ARP must not cache a group-addressed sender MAC"` covers the LAN ARP-request path with the same root cause/fix; not double-counted as a separate bug.

### SEC-STATE-04: an unsolicited ARP reply overwrites a live gateway cache entry, redirecting all WAN traffic to the attacker
- **Branch:** `bug/state-arp-gateway-overwrite`
- **Severity:** high
- **Component:** `src/protocols/arp.zig:135-151` (`.reply` handler) and `src/tables/arp_table.zig:69-96` (`cache` overwrites unconditionally)
- **Bug:** `Arp.handle` accepts any ARP reply whose `target_ip`/`target_mac` match this interface, and `ArpTable.cache` unconditionally overwrites an existing IP->MAC entry. - **Actual:** `ArpTable.cache` replaces the gateway entry with attacker_mac; a subsequent LAN->WAN packet is transmitted with Ethernet dst_mac = attacker_mac.
- **Repro test:** `test_fixtures/regression_tests.zig` test `"SEC-STATE-04: an unsolicited ARP reply must not overwrite the cached gateway mapping"` (fails on branch at the post-reply `lookup(gateway_ip) == gateway_mac` assertion).
- **Suggested fix (not applied):** record outstanding ARP requests (the waiter table already does) and only install/overwrite a mapping from a reply that matches one, or reject updates to a live entry whose MAC differs unless the entry has expired; consider pinning the DHCP-learned gateway mapping for the lease lifetime.
- **Notes:** distinct from SEC-FWD-05 (accepting a group/multicast sender MAC as a neighbour): that is about *wrong kind* of MAC; this is about overwriting a valid unicast mapping without solicitation. Compounded by SEC-STATE-02/03 but a different table and fix.
### SEC-PARSE-03: fragmented ICMPv4 echo requests are answered from the first fragment; the reply is emitted as an IP fragment
- **Branch:** `bug/parsing-icmp-fragment`
- **Severity:** medium
- **Component:** `src/protocols/ipv4.zig:169-181` (transport dispatch ignores `more_fragments` for offset-0 packets) and `src/protocols/icmpv4/echo.zig:53-107` (reply copies `buffer[0..frame_len]`, preserving the fragment's flags/identification)
- **Bug:** `IPv4.handle` sends every offset-0 packet to the protocol handler, including a *first fragment* (`more_fragments=1`). `ICMPv4.handle`/`Echo.handle` therefore parse and validate the first fragment's bytes as a complete ICMP message: the ICMP checksum is computed over the fragment only, and the echo handler replies by copying the original frame `buffer[0..frame_len]` after swapping addresses/TTL/type. That copy keeps `more_fragments=1` and the attacker-chosen IPv4 identification, so the router transmits an *IP fragment of an echo reply* generated from an incomplete datagram. The same first-fragment processing is done for ICMP error messages (destination-unreachable/time-exceeded) before any reassembly. A host receiving such a reply cannot deliver it as an echo reply (it waits for fragments that never arrive), and an attacker can make the router emit a fragment with attacker-chosen payload/identification toward a spoofed MAC/source on the LAN.
- **Trigger:** LAN frame -> IPv4 `src=192.168.86.42 dst=192.168.86.1`, `identification=0x7777`, `more_fragments=1`, `fragment_offset=0`, `total_length=36`, protocol 1 -> ICMPv4 echo request (`type=8`, `code=0`, id/seq/data, valid checksum for the fragment). The router answers with an Ethernet frame whose IPv4 header still has `more_fragments=1` and `identification=0x7777`.
- **Expected (safe):** do not act on an incomplete fragmented datagram: either reassemble the message (fragment table) before answering, or drop it. If a reply is generated, it must be a complete, non-fragmented IPv4 datagram (MF=0, offset=0, freshly chosen identification) whose ICMP checksum covers the whole reply message.
- **Actual:** the router emits one TX on LAN; parsing it back yields `more_fragments == true` (the test fails at `expect(!tx_ip.get(.more_fragments))`) with the request's identification. The positive control (same echo request with MF=0) is answered with a non-fragmented reply, proving only the fragment flag changes the behavior.
- **Repro test:** `test_fixtures/regression_tests.zig` test `"SEC-PARSE-03: a fragmented ICMPv4 echo must not be answered from its first fragment"` (fails on branch; full suite otherwise green).
- **Suggested fix (not applied):** in `IPv4.handle`, check `more_fragments` before dispatching to transport handlers for locally-addressed traffic (queue/reassemble or drop); and in `Echo.handle` build a fresh reply header (clear MF/offset, new identification) instead of copying the original header flags/ID.
- **Notes:** the test allows either drop or a correct reassembled reply, so a fix in either place passes. ICMP error handlers share the same first-fragment processing (`DestinationUnreachable`/`TimeExceeded`), so the same class of incomplete-message handling exists there; this test pins the echo path because its reply is directly observable.
### SEC-STATE-05: expired IPv4 fragment entries are never reclaimed unless another fragment arrives, retaining queued packet buffers
- **Branch:** `bug/state-frag-expired-retention`
- **Severity:** medium
- **Component:** `src/tables/ipv4_fragment_table.zig:120-129` (`get` reports an expired entry as absent but leaves it in the table), `:143-160` (`getOrCreate` is the *only* expiry sweep), `src/main.zig:96-104` (production loop expires ARP waiters but nothing expires fragment tables)
- **Bug:** Reassembly entries expire by deadline, but expiry is only acted on inside `IPv4FragmentTable.getOrCreate`, which runs on the next `append`/`resolve` (i.e. when some IP fragment is processed). `get()` returns `null` for an expired entry without removing it or releasing its queued buffers, and the production loop never calls any fragment-table expiry (`src/main.zig` calls `arp_waiters_table.expire` every iteration but has no equivalent for `lan_fragment_table`/`wan_fragment_table`). An unauthenticated LAN/WAN host can queue fragments for 256 keys x 16 fragments (= `capacity` x `MAX_PENDING_FRAGMENTS` = 4096 RX buffers, each up to the MTU) and then stop sending fragments; those buffers stay allocated until an unrelated IP fragment is seen or the process exits. This is a memory-retention DoS from packet-driven state, and it is also inconsistent with `ArpWaitersTable.get`, which releases expired queued buffers when it is called.
- **Trigger:** a non-first IPv4 fragment is queued into `IPv4FragmentTable`; its deadline passes (test uses a zero timeout for determinism) and `get()` is called for its key. Nothing else sweeps the table.
- **Expected (safe):** a lookup that observes an expired entry must reclaim it and release its queued buffers (and/or the forwarding loop must expire fragment entries periodically), so dead reassembly state cannot pin packet buffers indefinitely.
- **Actual:** `get()` returns `null` but the entry and its queued buffer remain; the tracking NIC sees 0 releases and `table.count()` stays 1 until `deinit`.
- **Repro test:** `src/tables/ipv4_fragment_table.zig` test `"SEC-STATE-05: looking up an expired fragment entry reclaims its queued buffers"` (module-local; fails on branch at the `nic.len == 1` assertion).
- **Suggested fix (not applied):** make `get` take `*IPv4FragmentTable` and evict/release expired entries like `ArpWaitersTable.get`, and add a periodic `expire(device)` call for both fragment tables in the forwarding loop.
- **Notes:** distinct from SEC-STATE-03 (NAT live-capacity fairness) - this is about *expired* state and buffer ownership, not live capacity. At scale the fill-and-idle attack is cheap and impactful: 256 keys x 16 fragments = 4096 packets (each a few dozen bytes on the wire) fill both fragment tables, after which the attacker stops and never needs to refresh, because expiry is never acted on without further fragment traffic. With the 16 KiB RX buffers the harness/Mock path allocates, that pins ~4096 x 16 KiB = 64 MiB per interface indefinitely (until an unrelated IP fragment arrives or the process exits); with production-sized buffers the byte total differs but the pin is the same. Because the attacker can idle, SEC-STATE-05's fix (reclaim on lookup / periodic expire) is what releases this; note that an attacker who *keeps refreshing* live entries instead can also hold the table at capacity, which additionally denies fragmented forwarding (same shape as SEC-STATE-03's fairness issue, not filed separately).
### SEC-PARSE-04: UDP checksum is validated over the IPv4 payload length instead of the UDP length, so RFC-invalid checksums are accepted
- **Branch:** `bug/parsing-udp-pseudo-length`
- **Severity:** low
- **Component:** `src/meta/checksum.zig:67-85` (`Checksum.addPseudoheader` uses `ip.total_length - ihl*4`) and `src/protocols/udp.zig:34-41` (`Udp.validate` calls it for UDP)
- **Bug:** For UDP the pseudo-header Length field is defined as the *UDP length* (RFC 768), but `addPseudoheader` always uses the enclosing IPv4 payload length (`total_length - ihl*4`, which is correct only for TCP, whose pseudo-header length is the TCP segment length). `Udp.parse` also accepts a UDP datagram whose length field is smaller than the IP payload, ignoring the trailing bytes at the UDP layer. The combination means the router verifies the UDP checksum over a pseudo-header whose Length differs from the one every RFC 768 endpoint uses: it accepts a datagram whose checksum is invalid per RFC 768 (invalid integrity check passes, NAT state is created and the corrupt datagram is forwarded) and it rejects a datagram whose checksum is valid per RFC 768 when the IP payload contains trailing bytes.
- **Trigger:** LAN Ethernet frame -> IPv4 `src=192.168.86.42 dst=8.8.8.8`, protocol 17 -> UDP header `src_port=40001, dst_port=53, length=8`, plus four trailing bytes after the 8-byte UDP header (IP payload 12). The UDP checksum is the one's-complement sum of the pseudo-header using Length=12 (the router's wrong value) over the 8-byte UDP header. It is *not* valid for Length=8 (the value in the UDP length field).
- **Expected (safe):** compute the UDP pseudo-header Length from the UDP `length` field (and treat a length/IP-payload mismatch as an invalid datagram); drop the packet before NAT, without creating a mapping or transmitting.
- **Actual:** `Udp.validate` accepts the datagram (`checksum.finish() == 0` with the 12-byte pseudo-length), `forwardNat` inserts a NAT mapping for 192.168.86.42:40001 and transmits the frame on WAN (`txCount == 1`, expected 0); `State.nat_table.inboundLookup({udp, 203.0.113.50, 40001})` is non-null. The positive control (length == IP payload, correct checksum) is forwarded as expected.
- **Repro test:** `test_fixtures/regression_tests.zig` test `"SEC-PARSE-04: UDP checksum must be validated over the UDP length, not the IPv4 payload length"` (fails on branch at `expectEqual(0, txCount)`; full suite otherwise green).
- **Suggested fix (not applied):** in `Udp.validate`, feed the UDP length to the pseudo-header computation (or use a UDP-specific `addPseudoheader` that takes the UDP length), and require `udp.length == ip.total_length - ip.ihl*4` (or at least `udp.length <=` the IP payload). `Tcp.validate` keeps using the IP payload length.
- **Notes:** the reverse direction (RFC-valid padded datagrams being dropped) follows from the same defect but is *not* asserted by this test; the Expected permits rejecting the mismatched length outright. End-to-end delivery is still gated by the destination's own RFC 768 check, so this is primarily a router-side validation/NAT-state bypass and a valid-packet-drop availability bug rather than a data-integrity break; a middlebox that trusts the router's accepted checksum would be bypassed. `Checksum.addPseudoheader` is also used by the DHCP transmit path, but the comment/behaviour there has matching length==payload, so tests are unaffected.
### SEC-STATE-06: NAT mappings (and ARP state) for a LAN address survive its DHCP lease being released, so the next lease holder inherits the previous holder's inbound traffic
- **Branch:** `bug/state-nat-outlives-dhcp-lease`
- **Severity:** medium
- **Component:** `src/protocols/dhcpv4.zig:391` (release), `src/tables/dhcp_table.zig:245-253` (`release` only touches the lease table), `src/tables/nat_table.zig` (no way to flush by inside IP)
- **Bug:** The DHCP server and the forwarding tables are independent state machines keyed only by address. - **Repro test:** `test_fixtures/regression_tests.zig` test `"SEC-STATE-06: NAT mappings for a LAN address are invalidated when its DHCP lease is released"` (fails on branch immediately after the DHCPRELEASE).
- **Suggested fix (not applied):** on `DhcpTable.release`/`decline`/expiry-reclaim, also flush NAT/ARP state for that address (e.g. `NatTable.removeAllForInsideIp(ip)` and an `ArpTable.remove(ip)`), or bind NAT mappings to the lease identity (client-id/MAC) so a different lease holder cannot match them.
- **Notes:** independent of SEC-STATE-01 (that one is the missing MAC check that lets an attacker trigger a release; this one is that even a *legitimate* release leaves the mappings). If a fix binds mappings to the lease, SEC-STATE-01's impact also shrinks.

### SEC-PARSE-05: DHCP client accepts an ACK assigning a non-unicast WAN address (loopback/broadcast/multicast), then uses it as its WAN identity
- **Branch:** `bug/parsing-dhcp-ack-invalid-ip`
- **Severity:** low
- **Component:** `src/protocols/dhcpv4.zig:488-497` (OFFER only rejects `0.0.0.0`) and `:456-481` (ACK accepts `your_ip` == the offered address without any address-class validation)
- **Bug:** The DHCP client takes the server-assigned address from the OFFER (`your_ip`, rejected only when exactly `ZERO_IP`) and accepts it in the ACK if it equals `transaction.requested_ip`; there is no check that the assigned address is a usable interface address. A loopback/broadcast/multicast source address emitted on the ISP link violates RFC 1122/BCP38; an arbitrary spoofed unicast value lets a DHCP server make the router originate all WAN traffic with a chosen third-party source address. It also changes `classifyDestination` (a LAN destination equal to the lease is classified `.local` and dropped).
- **Trigger:** driven end-to-end through the WAN DHCP client: `DHCPv4.tickWan` sends DISCOVER, a WAN BOOTREPLY OFFER (xid/chaddr match, server_id=203.0.113.1, mask 255.255.255.0, router 203.0.113.1, lease 3600, `your_ip=127.0.0.1`), `tickWan` sends REQUEST, then a matching ACK with message type 5 and `your_ip=127.0.0.1`.
- **Expected (safe):** reject an OFFER/ACK whose `your_ip` is not a usable unicast interface address (0.0.0.0/8, 127.0.0.0/8, 224.0.0.0/4, 240.0.0.0/4, and ideally not the subnet network/broadcast of the offered mask); leave `wan_lease` unset (and keep retrying/NAK-ing as appropriate).
- **Actual:** `State.wan_lease.ip` becomes `127.0.0.1` and the client considers the handshake complete; the test fails with `expected null, found {127,0,0,1}`.
- **Repro test:** `test_fixtures/regression_tests.zig` test `"SEC-PARSE-05: DHCP client must reject a WAN lease that assigns a non-unicast address"` (fails on branch). It includes a positive control: the identical handshake with `203.0.113.50` is accepted/installed, proving the transaction state machine is exercised correctly and only the assigned-address value differs.
- **Suggested fix (not applied):** add an `isUsableUnicastAddress()` check for `your_ip` in both the OFFER branch and before committing the ACK; reject loopback, unspecified/this-network, multicast, reserved/broadcast, and (optionally) addresses whose host part is all-zero/all-one under the offered mask.
- **Notes:** reachable only from a DHCP reply on the WAN (the ISP DHCP server or an on-path spoofer who can see the broadcast DISCOVER/xid and reply), so severity is kept low: an on-path DHCP attacker already controls the gateway, but this validation gap additionally lets the router be used to emit martian/spoofed source addresses and can blackhole a destination whose IP equals the lease. Same class of check would also cover a buggy (non-malicious) DHCP server.
### SEC-STATE-07: a single LAN host can reserve the entire DHCP pool with distinct client identifiers, denying DHCP service to the whole segment
- **Branch:** `bug/state-dhcp-pool-starvation`
- **Severity:** low
- **Component:** `src/tables/dhcp_table.zig:179-218` (`offer` keys allocation on the client identifier only) and `src/protocols/dhcpv4.zig:381-389`
- **Bug:** `DhcpTable.offer` treats the client identifier (option 61) as the sole identity and never limits how many `offered` entries one L2 source may hold. A single host can send one DISCOVER per address with a distinct, arbitrary client-id (all from the same MAC) and the server hands out an OFFER for every pool address (`OFFER_HOLD` = 30 s). While the offers are held the pool is empty, so legitimate clients get no OFFER and cannot obtain a lease. Re-sending the DISCOVERs every <30 s keeps the pool starved indefinitely. The attack is ~253 packets per 30 s for the production /24 pool; unlike SEC-STATE-01 it needs no spoofing of another client's identity and the addresses are not permanently lost, but it denies DHCP to every new client while active.
- **Policy assumption:** pool starvation is a well-known DHCP property and final mitigation needs switch-level DHCP snooping/port security; the test encodes the server-side hardening expected of a router that is both DHCP server and gateway: one L2 source must not be able to reserve more than a bounded share of the pool (per-MAC quota, or reclaiming the oldest offer when the pool is exhausted).
- **Trigger:** pool = {192.168.86.10, .11}; host MAC A sends DISCOVERs with client-ids "spoof-1", "spoof-2", "spoof-3"; a different host MAC B then sends a normal DISCOVER.
- **Expected (safe):** the legitimate client still receives an OFFER (bounded per-MAC allocation or oldest-offer reclamation).
- **Actual:** `offer` returns null (`pool.len == 0`, no expired entries yet), the handler drops the DISCOVER, and no DHCP reply is transmitted (TX count 0 instead of 1).
- **Repro test:** `test_fixtures/regression_tests.zig` test `"SEC-STATE-07: one L2 client cannot reserve the whole DHCP pool with distinct client identifiers"` (fails on branch at the post-attack `txCount() == 1` assertion).
- **Suggested fix (not applied):** cap `offered`/`bound` entries per L2 source (MAC) or per client-id prefix, and when the pool is exhausted reclaim the oldest `offered` entry instead of returning null; rate-limit OFFER generation per source.
- **Notes:** distinct from SEC-STATE-01 (permanent exclusion via DECLINE with a spoofed client-id) and from SEC-STATE-06 (state surviving a release). MAC spoofing can bypass a per-MAC quota, so this is defense-in-depth, not a complete fix.
### SEC-STATE-08: one LAN host can evict every live ARP entry with a spoofed-entry flood (cache eviction fairness)
- **Branch:** `bug/state-arp-cache-eviction`
- **Severity:** medium
- **Component:** `src/tables/arp_table.zig:82-93` (`cache` evicts the oldest entry when `len == capacity`, with no per-source accounting), `src/protocols/arp.zig:130,141` (learns `sender_ip -> sender_mac` from any request/reply, for any sender IP)
- **Bug:** `ArpTable` is a fixed 256-entry array. `cache` never refuses an entry and never bounds how many entries one sender may own: at capacity it evicts the oldest entry by timestamp. `Arp.handle` learns an entry from any ARP request/reply addressed to the router, with no on-link/ownership check. A single LAN host can therefore send 256 ARP messages from its own MAC with 256 distinct spoofed sender IPs (it does not need to own them) and flush every legitimate neighbour out of the cache, including recently learned LAN clients and (on the WAN table) the gateway. Once a real neighbour is evicted, the next packet for it is no longer forwarded directly: it is queued for ARP resolution (the first packet is held/dropped), the router re-ARPs, and any host that answers the re-ARP receives that traffic (see SEC-STATE-04). Repeating the flood also causes continuous re-resolution churn. Cost: one spoofed ARP reply per entry (256 tiny frames), and the table accepts off-link sender IPs, so the flood space is unbounded.
- **Policy assumption:** ARP caches are inherently unauthenticated and real caches do evict; the test encodes the fairness property a router should have: one unauthenticated sender must not be able to displace a legitimately learned neighbour with 256 spoofed entries (per-source entry quota and/or only caching senders the router can legitimately learn). Either mitigation makes the test pass.
- **Trigger:** router learns 192.168.86.42 -> victim_mac from a normal ARP reply; attacker sends 256 ARP replies with `sender_mac = attacker_mac` and `sender_ip = 10.0.0.0 .. 10.0.0.255`.
- **Expected (safe):** the legitimate neighbour 192.168.86.42 -> victim_mac is still present after the flood.
- **Actual:** the victim's entry is evicted (`lookup(192.168.86.42) == null`), so forwarding to it falls back to ARP resolution/queueing.
- **Repro test:** `test_fixtures/regression_tests.zig` test `"SEC-STATE-08: one LAN host flooding spoofed ARP entries must not evict a live neighbour"` (fails on branch at the post-flood `lookup(...) != null` assertion).
- **Suggested fix (not applied):** cap entries per sender MAC (and/or per interface subnet) and reject learning for sender IPs that are not on-link for the ingress interface; when the table is full and no evictable entry exists, drop the new entry instead of evicting an established one.
- **Notes:** distinct from SEC-STATE-04 (which is about *overwriting an existing mapping* from an unsolicited reply; fix = require a solicited reply) and from SEC-FWD-05 (group sender MAC). Same table as 04, different mechanism (capacity/eviction); both are amplified by it. If the fix for this is a per-MAC quota, SEC-STATE-04's attack still works (it overwrites rather than adding).
### SEC-STATE-09: one LAN host can monopolize the fragment table's live entries and deny reassembly/forwarding to every other flow
- **Branch:** `bug/state-frag-capacity-fairness`
- **Severity:** medium
- **Component:** `src/tables/ipv4_fragment_table.zig:143-160` (`getOrCreate` evicts only expired entries; at live capacity it returns `error.FragmentTableFull`), `src/protocols/ipv4.zig:136-167` (non-first fragment path queues before any NAT lookup)
- **Bug:** The reassembly table holds `capacity` (256 in `src/main.zig`) keys, each with up to `MAX_PENDING_FRAGMENTS` (16) queued buffers. Live entries are never evicted and there is no per-source accounting: `getOrCreate` only removes entries whose deadline has passed, and otherwise returns `error.FragmentTableFull`. The key is `(src, dst, identification, protocol)` and every field is attacker-chosen, so a single LAN host can create up to 65536 distinct keys from one source address by varying the 16-bit IP identification. Cost to fill every live slot is 256 small non-first fragments (they are queued before any NAT/lease work), and keeping them alive costs one fragment per key per fragment timeout (~8.5 packets/s). While the table is full, any other host's new fragmented flow is dropped: `forwardFirstFragment` gets `FragmentTableFull`, the error propagates out of `IPv4.handle`, and the first fragment is released (after `forwardNat` has already created/refreshed a NAT mapping for it). Up to 4096 RX buffers (~64 MiB in the harness/Mock path, 16 KiB each) are also pinned while the table is held. This is the fragment-table analogue of SEC-STATE-03's NAT capacity fairness gap.
- **Policy assumption:** a bounded table is by design, but the router should not let one unauthenticated source deny fragmented forwarding to everyone; the test only requires that a *different* host's first fragment is still forwarded, so either a per-source key quota or LRU eviction of live entries (when the table is full and nothing is expired) makes it pass.
- **Trigger:** pool-independent; harness uses `fragment_capacity = 4` for brevity. Attacker 192.168.86.42 sends 4 non-first fragments (offset 8, more_fragments=false, ids 1..4) to 8.8.8.8; victim 192.168.86.43 then sends the first fragment (id 7, more_fragments=true) of a UDP datagram to 8.8.8.8.
- **Expected (safe):** the victim's first fragment is NATed and forwarded to the WAN gateway (one TX), not dropped because the attacker owns every live reassembly slot.
- **Actual:** `resolve` fails with `FragmentTableFull`, the victim's packet is dropped (TX count 0 instead of 1, one handler error), so no new fragmented flow can be forwarded while the attacker keeps the table full.
- **Repro test:** `test_fixtures/regression_tests.zig` test `"SEC-STATE-09: one LAN host cannot monopolize the fragment table and deny reassembly to other flows"` (fails on branch at the post-victim `txCount() == 1` assertion).
- **Suggested fix (not applied):** when inserting hits live capacity, evict the oldest/least-recently-used live entry (and release its queued buffers) or enforce a per-source/per-key quota so one host cannot hold every slot.
- **Notes:** distinct from SEC-STATE-05 (expired entries retaining buffers — its periodic-expiry fix does not help here because the attacker's entries are live and refreshed) and from SEC-STATE-03 (same fairness shape, different table). In production the fill cost is 256 packets and ~8.5 packets/s to hold; the WAN fragment table has the same issue (WAN attacker).
### SEC-STATE-10: an ARP request also overwrites live neighbour mappings (WAN gateway and LAN client), giving the same WAN MITM as SEC-STATE-04 through a different trigger
- **Branch:** `bug/state-arp-request-overwrite`
- **Severity:** high
- **Component:** `src/protocols/arp.zig:107-134` request branch, `:130` (`table.cache(view.get(.sender_ip), view.get(.sender_mac))`); `src/tables/arp_table.zig:69-96` (`cache` overwrites unconditionally)
- **Bug:** The request branch learns the sender's `(ip, mac)` pair from every ARP request addressed to one of the router's own addresses and stores it unconditionally, with no solicitation/liveness/ownership check and with no "only if absent" restriction. Unlike SEC-STATE-04 (which is the reply branch), the trigger is an ARP *request*: the router answers it (fine) and then replaces whatever it had for the sender's IP with the request's sender MAC. A WAN on-link host that claims the gateway's IP therefore replaces the validated gateway mapping, and every subsequent LAN->WAN forwarded frame is sent to the attacker's MAC - the same full WAN man-in-the-middle as SEC-STATE-04, reachable with one spoofed ARP request. The LAN variant does the same to a live LAN neighbour, so the neighbour's inbound NAT traffic is delivered to the attacker.
- **Policy assumption:** ARP is unauthenticated and the project documents no ARP authority policy; this is the same hardening class as SEC-STATE-04 but a **distinct trigger and a distinct fix**: SEC-STATE-04's proposed fix ("only install a mapping from a reply that matches an outstanding request") does not touch the request branch, so fixing only replies leaves this attack open. The test encodes the rule a router should have: an ARP request may answer, and may create a *missing* entry, but must not overwrite an existing unexpired mapping for the sender address (or must validate that sender against the DHCP/ARP binding).
- **Trigger:** WAN ARP cache has gateway 203.0.113.1 -> gateway_mac (verified by a normal LAN->WAN TX); a WAN host sends an ARP request with `sender_mac = attacker unicast MAC`, `sender_ip = 203.0.113.1` (the gateway), `target_ip = 203.0.113.50` (the router's WAN lease IP). The router replies and caches `203.0.113.1 -> attacker_mac`; the next forwarded frame has Ethernet dst = attacker_mac. LAN variant: same request with `sender_ip = 192.168.86.43` (a live neighbour), `target_ip = 192.168.86.1`.
- **Expected (safe):** the request is answered but the validated gateway/neighbour entry is retained, so forwarding keeps using the real MAC (and inbound traffic for the LAN neighbour keeps going to the real host).
- **Actual:** `State.wan_arp_table.lookup(203.0.113.1)` becomes `02:66:66:66:66:66` (attacker) instead of `02:99:88:77:66:55` (gateway); the test fails at that assertion (`expected 02:99:88:77:66:55, found 02:66:66:66:66:66`). The LAN variant and the forwarding consequence checks are included and fail in the same way once the WAN assertion is passed by a fix.
- **Repro test:** `test_fixtures/regression_tests.zig` test `"SEC-STATE-10: an ARP request must not overwrite an existing neighbour mapping"` (fails on branch at the WAN gateway lookup; includes positive controls that the real gateway/neighbour MACs are used before the attack and consequence checks for both variants after it).
- **Suggested fix (not applied):** in the request branch, skip `table.cache` when an unexpired entry already exists for `sender_ip` (or only learn from requests whose `sender_ip` is `0.0.0.0` / not already known), and consider validating the sender MAC against the DHCP binding / a locked gateway mapping; apply SEC-STATE-04's reply-solicitation fix independently for the reply branch.
- **Notes:** distinct from SEC-STATE-04 (reply trigger; its fix leaves this open) and from SEC-FWD-05 (group sender MAC is a MAC-kind validation issue, not cache authority). The request branch also replies to a group sender MAC (SEC-FWD-05/FWD-04 class), but that is not the reported consequence here.
### SEC-PARSE-06: DHCP client installs an unusable `router` option as the default next-hop, so every WAN forward is ARP-blackholed or answerable by an off-path spoofer
- **Branch:** `bug/parsing-dhcp-gateway-invalid`
- **Severity:** low
- **Component:** `src/protocols/dhcpv4.zig:462-480` (ACK handling reads `options.router` / option 3 and stores it in `wan_lease.router` without any validation)
- **Bug:** The WAN DHCP client requires the OFFER/ACK to carry option 3 (router) but never checks that its value is a usable next-hop. An ACK whose router option is `0.0.0.0` (or 127/8, 224/4, 240/4, the subnet broadcast, or an otherwise off-link/loopback address) is accepted and installed as `wan_lease.router`. `IPv4.forward` uses `lease.router` as the next hop for every WAN egress (`forward(..., lease.router, ...)`), so `ARP` resolution is then performed for that invalid address: the router emits an ARP request for `0.0.0.0`/the multicast address and queues the traffic, blackholing all WAN forwarding. Any on-link host that answers that ARP can receive all NATed traffic (redirect/MITM); a buggy or malicious DHCP server can also silently disable WAN connectivity with an address that can never be a real gateway. Renewal next-hop selection (`tickWan`) is affected too when the DHCP server is considered off-link.
- **Trigger:** WAN DHCP handshake (DISCOVER -> OFFER -> REQUEST -> ACK) where the OFFER and ACK carry `option 3 = 0.0.0.0`, `option 54 = 203.0.113.1`, `option 1 = 255.255.255.0`, `option 51 = 3600`, and `your_ip = 203.0.113.50`. A positive control with router `203.0.113.1` is installed normally.
- **Expected (safe):** reject an ACK whose router option is not a usable unicast next-hop (0/8, 127/8, 224/4, 240/4, subnet broadcast; ideally require a unicast address on-link under the offered mask) and leave `wan_lease` unset, or fall back to a validated next hop. The subsequent LAN->WAN datagram must not trigger an ARP request for `0.0.0.0`.
- **Actual:** `State.wan_lease.router == 0.0.0.0`; the test fails with `expected null, found {0,0,0,0}` at the "lease router must not be 0.0.0.0" assertion. Positive control proves the handshake/state machine itself is exercised.
- **Repro test:** `test_fixtures/regression_tests.zig` test `"SEC-PARSE-06: DHCP client must reject an ACK whose router option is an unusable next-hop"` (fails on branch; full suite 123/124 with only this failure).
- **Suggested fix (not applied):** validate option 3 (and the renewal path) as a usable unicast address, ideally on-link under the offered subnet mask; reject the ACK/option otherwise. Apply the same address-class helper used for `your_ip` in SEC-PARSE-05.
- **Notes:** distinct from SEC-PARSE-05 (that report covers the `your_ip`/lease-address class); this covers the `router`/next-hop option. Requires WAN DHCP control (ISP-level/on-path threat model), so severity is low: an ISP can already drop traffic, but this gap makes the router's forwarding depend on an unvalidated DHCP-supplied address and exposes an ARP-based redirect surface.
### SEC-STATE-11: LAN ingress trusts any IP source, so a LAN host can create NAT pinholes for another host (and spoof arbitrary inside addresses)
- **Branch:** `bug/state-nat-lan-source-spoof`
- **Severity:** medium
- **Component:** `src/protocols/ipv4.zig:201-243` (`forwardNat` `.lan` branch builds the NAT key from `ip_view.get(.src)` with no ingress source validation); `src/tables/nat_table.zig:133-176` (`insert`)
- **Bug:** The LAN->WAN path believes whatever IP source the frame carries. It never compares the source address with the ingress interface's ARP binding for the frame's Ethernet source MAC, nor with the DHCP lease table, before creating a NAT mapping and forwarding. A malicious LAN host can therefore send a datagram with **another LAN host's source address** (or any address the router will route back on the LAN) and the port of a service that host runs. The router creates a mapping whose inside key is the victim's address and forwards the datagram; a remote party that knows the external port can then reach the victim's port through the router even though the victim never sent anything. The same primitive lets a LAN host create mappings keyed by arbitrary inside addresses (unassigned, the gateway's own address, martian values), which also feeds NAT state pollution (SEC-STATE-03) and the address/authority games in SEC-STATE-10.
- **Policy assumption:** LAN source filtering (DHCP snooping / ARP-binding ingress filtering) is a hardening expectation, not a documented requirement of this project - a typical home router trusts the LAN. It is reported because the audit's threat model explicitly includes a malicious LAN device and the NAT is the only firewall, so a pinhole around it is a real boundary bypass; the test only requires that a datagram is not forwarded and creates no mapping unless its link-layer sender owns the source address, and keeps the victim's own flow working.
- **Trigger:** victim 192.168.86.43 is bound to victim_mac in the LAN ARP cache. Attacker MAC A sends a LAN Ethernet frame (`eth src = A`) with IPv4 src = 192.168.86.43, UDP src port 8080, dst 8.8.8.8:53. The router creates the mapping 203.0.113.50:8080 -> 192.168.86.43:8080 and forwards the datagram; a WAN host then sends to 203.0.113.50:8080 and the router delivers it to the victim's port.
- **Expected (safe):** drop the datagram (no NAT mapping, no WAN transmission) because its link-layer sender does not own the IP source; the victim's own datagrams must still be NATed and delivered normally.
- **Actual:** the mapping is created (`State.nat_table.inboundLookup((udp, 203.0.113.50, 8080))` is non-null) and the frame is transmitted (test fails at the `inboundLookup(...) == null` assertion; the external-reach consequence check is included and also fails without a fix).
- **Repro test:** `test_fixtures/regression_tests.zig` test `"SEC-STATE-11: a LAN host spoofing another host's source address must not create NAT pinholes for it"` (fails on branch at the post-attack `inboundLookup(...) == null` assertion; includes the victim positive control and a post-fix external-reach check).
- **Suggested fix (not applied):** in `forwardNat`'s `.lan` branch, validate `ip_view.get(.src)` against the ingress ARP binding (the frame's Ethernet source MAC must match the cached MAC for that IP) and/or the DHCP lease table before inserting a mapping; drop otherwise. This is the LAN-side counterpart of SEC-FWD-02's WAN-ingress source validation.
- **Notes:** distinct from SEC-FWD-02 (WAN-ingress sources), SEC-STATE-02 (peer direction of inbound lookups), SEC-STATE-06 (mappings surviving a release), SEC-STATE-10 (ARP cache authority) and SEC-STATE-03 (capacity). Same trust class as SEC-STATE-08/10, but the state created is a firewall/NAT pinhole for a *third party*, which none of them cover.

### SEC-FWD-07: Ethernet bytes after the IP datagram are forwarded across interfaces (L2 trailing-byte smuggling)
- **Branch:** `bug/forwarding-trailing-bytes`
- **Severity:** low
- **Component:** `src/protocols/ipv4.zig:395-421` (`forward` calls `device.transmit(buffer)` with the whole received frame), reached from `forwardNat` (`:228-242`), `forwardFragment` (`:382-391`); contrast `src/protocols/icmpv4/echo.zig:91-105` and `src/protocols/icmpv4/time_exceeded.zig:93-105`, which bound the emitted length.
- **Bug:** `Ethernet.parse` keeps every byte after the ethertype in `payload` (EtherType II frames), `IPv4.parse` consumes only `total_length` bytes of it, and `IPv4.forward` transmits the **entire original buffer**. Any L2 bytes between the end of the IP datagram and the end of the Ethernet frame therefore cross to the other interface byte-for-byte. Frames the router builds itself (echo reply, time-exceeded, DHCP, ARP) are serialized with an explicit length and do trim, so the forwarding path is the inconsistent one. A LAN host can hide an arbitrary trailer after a minimal IP datagram and have it delivered on the WAN link (and a WAN sender can deliver one to a LAN client), invisible to egress/ingress inspection that trusts the IP total length; it also lets the actual frame length disagree with the IP length (MTU/padding confusion).
- **Trigger:** LAN frame: Ethernet dst = router LAN MAC, 0x0800, then a valid 28-byte IP+UDP datagram (`total_length = 28`, empty UDP payload, valid checksums) followed by 200 bytes of `0xA7`. The router NATs the datagram and transmits a **242-byte** frame on the WAN (14 + 28 + 200) instead of a 42-byte frame; with one 802.1Q tag it transmits 246 bytes instead of 46. A WAN reply carrying the same trailer is forwarded to the LAN client as 242 bytes.
- **Expected (safe):** the egress frame must end at L2 header + IP `total_length` (42 bytes untagged, 46 with one tag) - the trailer must be dropped (or the frame dropped). No byte beyond the IP datagram may cross an interface.
- **Actual:** the trailer is forwarded intact: `tx.bytes.len == 242` for the untagged LAN->WAN case and all 200 marker bytes are present; the test fails with `expected 42, found 242`. Positive control: an echo request with the same trailer produces a 42-byte trimmed reply, confirming generated replies already bound the length.
- **Repro test:** `test_fixtures/regression_tests.zig` test `"SEC-FWD-07: L2 bytes after the IP packet must not be forwarded across interfaces"` (fails on branch at the first LAN->WAN length assertion; covers untagged LAN->WAN, VLAN-tagged LAN->WAN, WAN->LAN, and a generated-reply control).
- **Suggested fix (not applied):** in `IPv4.forward` transmit `buffer[0 .. l2_header_len + ip_total_length]` clamped to `buffer.len` (the L2 header length is 14 + the parsed tag stack), or trim the frame once in `Ethernet.handle` before dispatch; fragment and quoted-error forwarding use the same `forward` path and inherit the fix.
- **Notes:** distinct root cause from SEC-FWD-06 (the ingress VLAN tag stack is copied) - a tagged forward currently ships both the tag and the trailer, and fixing one does not fix the other. The trailer is outside every checksum, so it is not covered by the parser checksum checks. Requires a cooperating inside host plus an outside receiver (or a WAN sender plus a mapped port for the reverse), hence low severity.
